# 角色权限、账务规则与资金计算

[← 返回主 README](../README.md)

本文说明系统的三角色权限体系、核心账务规则、资金规划公式、多币种部分报销及汇率 API 策略。Web、飞书、Telegram 与 AI 助手均共用同一套规则与权限校验。

---

## 1. 成员角色与权限矩阵

成员的准入、角色分配（`owner` / `finance` / `member`）、账号启停与管理审计日志全部由 **Vanora OAuth** 集中管理。在 Vanora 私有管理后台为账号（或所属用户组）分配 `team-ledger` 客户端角色后，成员登录或触发同步时会自动在账本内投影为对应角色；当账号同时拥有多个角色时，按 **`owner > finance > member`** 优先级取最高权限；未分配任何客户端角色的账号将被拒绝登录。

| 能力 | 普通成员 (`member`) | 财务管理员 (`finance`) | 账本所有者 (`owner`) |
| --- | --- | --- | --- |
| 查看团队流水、报销列表、总览、只读成员名录与资金汇总 | 支持 | 支持 | 支持 |
| 资金计算试算 / 模拟新进账（不入账） | 支持 | 支持 | 支持 |
| 新增 / 编辑 / 提交 / 作废**本人未报销**的成员垫付 | 支持 | 支持 | 支持 |
| 上传 / 替换**本人未报销**垫付的凭证 | 支持（部分报销后锁定） | 支持 | 支持 |
| 修改个人显示名称、跳转 Vanora 账户中心 | 支持 | 支持 | 支持 |
| 新增「公账支出」「团队收入」或代他人记账 / 改垫付人 | — | 支持 | 支持 |
| 管理其他成员的未报销账目与凭证 | — | 支持 | 支持 |
| 登记单笔 / 批量报销付款（含机器人一键报销） | — | 支持 | 支持 |
| 永久删除已作废账目 | — | 支持 | 支持 |
| 导出 CSV 账目报表 | — | 支持 | 支持 |
| 手动点击「同步成员权限」刷新只读名录 | — | 支持 | 支持 |
| 绑定 / 解绑本人的飞书与 Telegram | 支持 | 支持 | 支持 |
| 在只读成员名录查看直达 Vanora 管理后台入口 | — | — | 支持 |
| 配置「团队设置」（团队名、币种、群聊允许名单） | — | — | 支持 |
| 在「机器人与 AI」配置飞书应用与 AI 记账引擎 | — | — | 支持 |
| 管理「数据备份与恢复」 | — | — | 支持 |

### 集中权限同步与实时撤销说明

- **Vanora OAuth 为唯一权限真源**：账本内不提供本地添加成员、邀请链接、修改角色或停用成员界面，所有成员管理与权限审计日志（Admin Events）均在 Vanora 私有管理后台完成。`team-ledger` 本地 `users` 表仅作为只读成员投影维护外键关联（历史账目、报销付款、飞书 / Telegram 绑定），成员可继续通过「个人资料」自定义在账本内的显示名称。
- **双通道实时撤销**：
  1. **事件驱动推送（OIDC Back-channel Logout）**：在 Vanora 管理后台变更成员的客户端角色、组归属、启用状态或删除用户后，Vanora OAuth 自动断开其客户端会话并推送签名 Logout Token（附带 `https://vanora.dev/events/permissions-changed` 或 `https://vanora.dev/events/account-deleted`），`team-ledger` 立即注销 Web 会话、清空未执行的 AI 操作清单、付款汇率报价、绑定码及机器人草稿/卡片状态并回拉最新角色。
  2. **TTL 周期校验**：Web、飞书与 Telegram 也会按 `VANORA_OIDC_PERMISSIONS_TTL`（默认 30 秒）自动向 `GET /realms/vanora/vanora-permissions/members/{sub}` 校验最新角色与启用状态，即使发生短暂网络故障也能在 TTL 内自动收敛。
- **零信任准入**：未在 Vanora OAuth 分配 `owner` / `finance` / `member` 任一客户端角色的账号无法登录，也无法通过机器人记账。详情见 [Vanora OAuth 客户端与集中权限接入](deployment.md#3-vanora-oauth-客户端与集中权限接入)。

## 2. 账务模型与核心规则

系统仅围绕三类账目运作，**没有审批流、没有分类标签、没有盈利分红**：

1. **公账支出（`public`）**：由团队公账直接支付。草稿不扣款，确认入账（`已入账`）后直接扣减公账可用余额，不进入待报销队列，也不参与报销预算、项目勾选或一键报销；作废后恢复对应余额。账目中的成员字段记录经手人。
2. **成员垫付（`advance`）**：由成员个人先垫款。确认记账后进入 `待报销`；只有在实际向成员转账并**登记本次已报销金额**后，才按真实付款币种与金额扣减公账余额。支持分次报销（界面标记为 `部分报销`）。
3. **团队收入（`income`）**：入账后增加公账可用余额；已作废收入不计入可用资金。

### 关键流转规则

- **无审核直报**：财务管理员与账本所有者可直接登记报销付款，无需其他成员审批；每次操作均记录操作人、时间与备注，可在账目详情的「操作记录」与「付款记录」中追溯。
- **修改与锁定**：尚未产生任何报销记录的草稿、待报销垫付和已入账公账支出允许编辑；成员垫付一旦产生部分或全部报销记录，立即锁定金额、币种、垫付人等编辑（防止破坏历史对账），普通成员亦不可再替换该笔凭证。
- **作废与永久删除**：尚未付款的账目可填写原因作废；已有任何报销记录的支出不允许作废。已作废账目默认不出现在总览、收支明细与机器人最近账目，可在 Web「报销管理 → 已作废」或机器人已作废列表中查看；财务管理员与账本所有者二次确认后可**永久删除**（账目、操作记录、付款记录和凭证文件将一并不可逆清除）。
- **选填说明与备注**：记账用途 / 收入说明和备注均为选填，留空亦可保存草稿或入账；列表界面展示为「未填写说明」，原始数据库与 CSV 导出保留空值。
- **高精度存储**：每笔记录保留原始币种与金额，按币种最小单位以整数存储（`decimals` 支持 `0` / `2` / `3` / `4` 位；默认人民币 / 美元 / 欧元 / 港币为 2 位，日元为 0 位），服务端统一用 `Decimal` 运算；已被账目或付款引用的币种禁止删除或修改小数位。
- **凭证与导出**：支持上传单文件 ≤ 6 MB 的 PNG / JPG / PDF 凭证（服务端校验文件魔数）。Web 报销列表与账目详情支持在弹窗内直接预览图片（支持原尺寸切换）与 PDF，并支持新标签打开与直接下载（兼容飞书内置浏览器）。CSV 导出使用 UTF-8 BOM 编码、金额与币种分列，并对 `=`、`+`、`-`、`@`、Tab、CR 前缀做公式注入防护。
- **旧版自动迁移**：升级启动时自动执行幂等迁移：
  - 原待审核 / 已审核未付款支出自动转为 `待报销`，已驳回支出回到 `草稿`。
  - 旧版已全额报销账目自动补齐一条历史付款明细，保留原日期、备注与金额。
  - 原盈利分红记录及更早的已分配收入自动转换为历史「公账支出」，保留原金额、币种、操作人、备注、时间与汇率快照，公账余额不变。

## 3. 公账支出与成员垫付示例

假设团队收到公账收入 `1,000 CNY`：

1. 公账支付服务器费用 `200 CNY`（公账支出）→ 公账可用余额 `800 CNY`，待报销 `0 CNY`。
2. 成员垫付打车 `100 CNY`（成员垫付）→ 公账可用余额仍为 `800 CNY`，待报销 `100 CNY`。
3. 实际转账报销其中 `40 CNY` → 公账可用余额 `760 CNY`，待报销 `60 CNY`。

## 4. 资金如何计算

「资金计算」以团队设置的参考币种统一换算汇总（可临时切换查看参考币种）：

```text
可用资金       = 团队收入 − 公账支出 − 已报销付款
全部待报销     = 所有待报销支出的未报销余额
本次报销范围   = 全部待报销，或手动勾选项目的未报销余额
本次安排报销   = min(max(可用资金, 0), 本次报销范围, 本次报销预算)
安排后结余     = 可用资金 − 本次安排报销
安排后仍待报销 = 全部待报销 − 本次安排报销
资金缺口       = max(全部待报销 − max(可用资金, 0), 0)
可安排付款     = 本次安排报销
```

例如：收到 `1,000 USD`（假设参考汇率 `1 USD = 7 CNY`），当前待报销 `3,000 CNY`，无此前收支，则本次预留 `3,000 CNY`，安排后结余 `4,000 CNY`。

### 三种安排模式与收入模拟

- **自动安排（默认）**：按发生日期从早到晚自动覆盖全部待报销。
- **指定报销预算**：按当前汇总参考币种设定本次上限（可填 `0` 暂不安排），优先覆盖日期最早的项目，余额或预算不足时显示某笔的部分安排。
- **手动选择报销项目**：仅对勾选项目安排报销（不勾选则不安排任何项目）。
- **模拟新进账**：可输入一笔**尚未入账**的新收入叠加到当前可用资金中进行预演。模拟不会写入账本或修改真实余额；已入账的收入请勿重复输入模拟。
- **伙伴报销明细**：展开到具体项目，列出用途、原币种金额、参考换算金额与建议付款金额，并标注全额 / 部分 / 暂不安排。

> **口径提示**：汇总采用当前获取或缓存的每日参考汇率对历史原币种金额重新换算，仅作资金规划参考，**不是历史锁定记账汇率、银行实际换汇成交价或会计利润**。系统不会自动执行银行或链上转账；多币种余额之间能否直接挪用付款需由团队自行确认。

## 5. 部分报销与跨币种付款

财务管理员或账本所有者在 Web 账目详情或报销管理点击「登记已付款」时，可单笔或批量填写**本次实际付款金额**（注意填写的是本次金额，而非累计值）：

- **付款币种选择**：每笔可选择按 **原记账货币**，或按团队设置的 **结算货币（汇总参考币种）** 登记。
- **跨币种示例**：原记账 `100 USD`，结算货币为 `HKD`，确认时参考汇率 `1 USD = 7.80 HKD`。本次实付 `312 HKD` 抵扣 `40 USD`，累计已报 `40 USD`、剩余 `60 USD`；下次仍可改用 `USD` 结清余款。
- **30 分钟汇率报价**：跨币种付款会锁定一份 30 分钟有效的参考汇率报价，并与当前账目版本绑定；确认后永久保存实际付款金额 / 币种、抵扣的原币金额、汇率快照、日期、操作人与备注。资金余额按实际付款币种与金额扣减，历史已确认付款不再随未来汇率变化重算。
- **避免尾差**：按币种最小单位四舍五入；填写界面给出的「剩余全额」对应金额可直接结清原账剩余，不留尾差。若汇率接口暂时不可用，仍可继续按原记账货币登记付款。

## 6. 汇率 API

默认使用 [Frankfurter](https://frankfurter.dev/) 公开接口，无需 API Key：

```dotenv
FX_API_URL=https://api.frankfurter.app/latest
FX_CACHE_HOURS=12
```

- 同时兼容 Frankfurter v1（`base/date/rates`）与 v2（如 `https://api.frankfurter.dev/v2/rates` 数组结构）。
- 数据为每日参考汇率（周末或节假日通常返回最近工作日），界面展示每对汇率的来源与日期。
- 同币种汇总不请求外部汇率接口。
- 汇率缓存与账目一同保存在 SQLite（`fx_cache` 表）；外部接口失败但本地有缓存时，界面明确标注使用缓存及其日期。
- 若某币种缺少汇率且无缓存，系统暂停跨币种合并计算，原币种账目仍可正常查看与记账。
- 仅汇率服务商支持的币种可自动换算；在团队设置中自行新增币种不保证上游 API 支持。
